## 2. Generating Longer Runs with a Loser Tree

The basic run-generation method from Lecture 01 loads $k$ records into memory, sorts them, and writes a run of length $k$. This produces approximately $n/k$ runs.

A better method, commonly called **replacement selection**, keeps a min loser tree in memory and replaces each record as soon as it is written. A new record may join the current run if it preserves sorted order; otherwise, it is saved for the next run.

**Memory organization**

- Two input buffers allow one buffer to be processed while another is filled from disk.
- Two output buffers allow one buffer to be filled while another is written to disk.
- The remaining memory stores a min loser tree.
- The lecture notes that three buffers can be sufficient, although the four-buffer layout makes the overlap easy to visualize.

<img src="./assets/image-20260718050401258.png" alt="image-20260718050401258" style="zoom:50%;" />

*The loser tree occupies most of memory, while input and output buffers connect it to disk.*

In steady-state operation, the following activities proceed concurrently:

1. Read the next input block from disk.
2. Generate the current sorted run using the CPU.
3. Write a completed output block to disk.

<img src="./assets/lecture02-overlapped-io.png" alt="Overlapping disk input, disk output, and run generation" style="zoom: 33%;" />



#### **Replacement-selection algorithm**

Assume the loser tree has $k$ external nodes.

1. Fill the tree with $k$ input records and initialize it as a min loser tree.
2. Remove the minimum active record and append it to the current run.
3. Read the next input record and compare it with the record most recently written:
   - If `newRecord >= lastOutput`, insert it as an **active** record for the current run.
   - If `newRecord < lastOutput`, mark it as **frozen** because writing it now would break the sorted order. It will participate in the next run.
4. Replay the loser tree to find the next minimum active record.
5. When every record in the tree is frozen, close the current run, unfreeze the records, and begin a new run.
6. Continue until the input is exhausted and all records have been written.

*Conceptually, every frozen record is treated as larger than every active record, regardless of its actual key.* This ensures that active records finish the current run before any frozen record is selected.

```text
lastOutput = -∞
initialize min loser tree with k records

while records remain in the tree:
    if every player is frozen:
        close current run
        unfreeze all players
        lastOutput = -∞

    winner = minimum active record
    write winner to current run
    lastOutput = winner.key

    if another input record exists:
        replacement = read next record
        if replacement.key < lastOutput:
            freeze replacement for the next run
        replace winner with replacement
    else:
        remove the winner's player

    replay the loser tree
```

## 3. Optimal Merging and Weighted External Path Length

*From here we are building the path to learn Huffman tree, (below are not tournament trees.)*

<img src="./assets/image-20260718120345127.png" alt="image-20260718120345127" style="zoom:50%;" />

When runs have different lengths, merge order affects the total amount of work. *A short run placed near the top of a merge tree is processed repeatedly, while a run connected directly to the root is processed only once.* 

> [!IMPORTANT]
>
> Let an external node represent an initial run, with its run length as the node's weight. The **weighted external path length (WEPL)** of a tree $T$ is:
>
> $$
> \operatorname{WEPL}(T)
> = \sum_i w_i d_i
> $$
>
> where:
>
> - $w_i$ is the weight or length of external run $i$.
> - $d_i$ is the distance of that external node from the root.
>

==WEPL equals the total merge cost== because a record is read and merged once for every merge level on the path from its initial run to the root.

**Example: runs of lengths $4,3,6,$ and $9$**

A balanced merge order gives:

<img src="./assets/image-20260718122101477.png" alt="image-20260718122101477" style="zoom:25%;" />

```text
4 + 3 = 7
6 + 9 = 15
7 + 15 = 22
Total merge cost = 7 + 15 + 22 = 44
```

Equivalently:

$$
\operatorname{WEPL} = 4(2)+3(2)+6(2)+9(2)=44
$$

A better merge order combines the smallest runs first:

<img src="./assets/image-20260718122125831.png" alt="image-20260718122125831" style="zoom:25%;" />

```text
3 + 4 = 7
6 + 7 = 13
9 + 13 = 22
Total merge cost = 7 + 13 + 22 = 42
```

$$
\operatorname{WEPL} = 4(3)+3(3)+6(2)+9(1)=42
$$

<img src="./assets/lecture02-optimal-merge-tree.png" alt="Optimal merge tree for runs of lengths 4, 3, 6, and 9 with WEPL 42" style="zoom:50%;" />

The second tree is better because the longest run, of length 9, is merged only once. 

> [!TIP]
>
> The problem of finding a binary merge tree with minimum WEPL is exactly the problem solved by a **Huffman tree**.

## 4. Other applications of optimal merge trees

<img src="./assets/image-20260718122959105.png" alt="image-20260718122959105" style="zoom:50%;" />

Optimal merge trees also solve <u>message-coding</u> and <u>lossless-compression problems</u>.



### Message coding and decoding

<img src="./assets/image-20260718123751408.png" alt="image-20260718123751408" style="zoom:50%;" />

If message $M_i$ has a code of length $l_i$, its contribution to the transmission cost is $f_i l_i$. Therefore:

$$
\text{transmission cost}
= \sum_i f_i l_i
$$

A binary decoding tree assigns `0` to one branch and `1` to the other. Each message is stored at an external node, so its code length equals its depth. Consequently:

$$
\text{transmission cost}
= \text{decoding cost}
= \operatorname{WEPL}
$$

> **Prefix property**
>
> A valid variable-length code must be **prefix-free**: no complete code may be the prefix of another code. Otherwise, the decoder would not know where one code ends.
>
> Every binary tree whose messages occupy only leaves defines a prefix-free code. Starting at the root, follow the edges labelled `0` and `1` until reaching a message leaf. -> binary tree approach doesn't have this prefix issue, things leaf nodes like 00 and 001 both can't be exist together



**Message-frequency example**

<img src="./assets/image-20260718123959131.png" alt="image-20260718123959131" style="zoom:50%;" />


$$
2(2)+4(2)+8(2)+100(2)=228
$$

<img src="./assets/image-20260718130846785.png" alt="image-20260718130846785" style="zoom:50%;" />

A variable-length prefix code can use:

| Message | Message frequency | Code | Code length |
| ---: | --- | ---: | ---- |
| M~1~ | 2 | `000` | 3 |
| M~2~ | 4 | `001` | 3 |
| M~3~ | 8 | `01` | 2 |
| M~4~ | 100 | `1` | 1 |

Its cost is:

$$
2(3)+4(3)+8(2)+100(1)=134
$$

<img src="./assets/lecture02-variable-length-code.png" alt="Variable-length prefix-code tree with decoding cost 134" style="zoom:50%;" />

The frequent message receives the shortest code, which reduces the weighted cost from 228 to 134. -> *so using minimized WEPL reduces transmission cost as well as decoding cost*

<img src="./assets/image-20260718131208672.png" alt="image-20260718131208672" style="zoom:50%;" />



### **Lossless-compression**

Suppose an alphabet has the following symbol counts:

| Symbol | Frequency |
| --- | ---: |
| `a` | 10 |
| `b` | 5 |
| `c` | 100 |
| `d` | 900 |

Using a fixed two-bit code requires:

$$
10(2)+5(2)+100(2)+900(2)=2030\text{ bits}
$$

Using the prefix code `a = 000`, `b = 001`, `c = 01`, and `d = 1` requires:

$$
10(3)+5(3)+100(2)+900(1)=1145\text{ bits}
$$

The compression ratio, excluding the code table, is approximately:

$$
\frac{2030}{1145}\approx1.8
$$

For example, the bit string `0001100101...` is decoded as:

```text
000 | 1 | 1 | 001 | 01 | ...
 a  | d | d |  b  | c  | ...
```

<img src="./assets/lecture02-prefix-code-decoding.png" alt="Prefix-code decoding tree for symbols a, b, c, and d" style="zoom:50%;" />

Maximum compression is obtained when the decoding tree has minimum WEPL.

## 5. Huffman Trees

<img src="./assets/image-20260718132907894.png" alt="image-20260718132907894" style="zoom:50%;" />

> [!CAUTION]
>
> Huffman Tree is not a tournament tree
>
> |                    | Huffman Tree                                        | Tournament Tree                       |
> | ------------------ | --------------------------------------------------- | ------------------------------------- |
> | **Purpose**        | Data compression / encoding                         | Finding min/max efficiently           |
> | **Leaves**         | Symbols with frequencies                            | Elements being compared               |
> | **Internal nodes** | Combined frequencies                                | Winner of comparisons                 |
> | **Construction**   | Repeatedly combine the **two smallest frequencies** | Pairwise comparisons between elements |
> | **Main use**       | Huffman coding                                      | Selection, sorting, k-way merging     |

### 1. Binary Huffman Trees

A **Huffman tree** is a tree with minimum weighted external path length. Its leaf depths define **Huffman codes**.

> [!NOTE]
>
> For a binary tree, a greedy algorithm constructs an optimal tree:
>
> 1. Start with one single-node tree for every weight.
> 2. Remove the two trees with the smallest weights.
> 3. Create a new root with those trees as its children. -> number of total trees will be reduced by 1 in each tree creation.
> 4. Give the new tree a weight equal to the sum of its children's weights.
> 5. Insert the new tree back into the collection.
> 6. Repeat until only one tree remains.
>

**Worked example: weights `[2, 5, 4, 7, 9]`**

```text
2 + 4  = 6
5 + 6  = 11
7 + 9  = 16
11 + 16 = 27
```

The WEPL is the sum of the combined weights:

$$
6+11+16+27=60
$$

### 2. Higher-Order Huffman Trees

> Huffman tree only gives what's the best possible way to select runs to do a k-way merge in our merge sort context. -> improve merging (stage 2) by reducing cost. 
>
> Tournament tree -> can be used to generate longer runs (improvement) and to do k-way merge

For a $k$-ary tree with $k>2$, repeatedly combining the $k$ smallest weights works only when the final tree can be a **full $k$-ary tree**, meaning every internal node has exactly $k$ children.

**Why the naïve greedy method can fail**

For a three-way tree with weights `[3, 6, 1, 9]`, immediately combining the three smallest real weights gives:

```text
1 + 3 + 6 = 10
10 + 9 = 19
Cost = 10 + 19 = 29
```

<img src="./assets/image-20260718160941765.png" alt="image-20260718160941765" style="zoom: 33%;" />

The final root has only two children. Treating the missing child as a zero-weight dummy gives a better construction:

```text
0 + 1 + 3 = 4
4 + 6 + 9 = 19
Cost = 4 + 19 = 23
```

<img src="./assets/lecture02-ternary-greedy-failure.png" alt="Naive and optimal three-way Huffman trees with costs 29 and 23" style="zoom:50%;" />

**Number of zero-weight dummy nodes**

Let:

- $r$ be the initial number of real weights or runs.
- $q$ be the number of zero-weight dummy runs added.
- $k$ be the tree order.
- $s$ be the number of $k$-way merges.

Each K-way merge reduces the number of trees by $k-1$ (by removing K trees and adding 1 tree). To finish with exactly one tree:

$$
total\ trees=r+q-s(k-1)=1
$$

Therefore:

<img src="./assets/image-20260718164532197.png" alt="image-20260718164532197" style="zoom:67%;" />
$$
(r+q-1)\bmod(k-1)=0
$$

The least non-negative valid value is:

$$
q=(1-r)\bmod(k-1), \qquad 0\leq q<k-1
$$

Examples:

- For $k=2$, $k-1=1$, so $q=0$ for every $r$. Binary Huffman coding never needs dummy weights.
- For $k=4$ and $r=6$:

$$
q=(1-6)\bmod3=(-5)\bmod3=1
$$

One dummy run is added, giving seven starting runs before applying the four-way greedy algorithm.

## 6. Buffering an External $k$-Way Merge 

An efficient $k$-way merge must keep the CPU busy while disk reads and writes occur in the background.

**Memory partition**

- Exactly two output buffers are used so one can be written while the other is filled.
- At least $k+1$ input buffers are required for a $k$-way merge. as input
- A total of $2k$ input buffers is sufficient when buffers are allocated dynamically.
- The remaining memory is used by the loser tree and control structures.

Permanently assigning two input buffers to every run is ineffective: one run may need several prefetched blocks while buffers assigned to other runs remain unused. Instead, each run has a queue of available buffers and all unassigned buffers are kept in a shared free pool.

<img src="./assets/lecture02-k-way-buffer-layout.png" alt="Dynamic input-buffer queues and a shared free-buffer pool for a nine-way merge" style="zoom:50%;" />

**Predicting which run will exhaust first**

To decide where the next free input buffer should be allocated:

1. Examine the key of the last record currently buffered from each run.
2. The run with the smallest last key is expected to exhaust its available buffered data first.
3. Use a consistent tie-breaker if multiple runs have the same last key.
4. Prefetch the next block of that run into a free buffer.

Because every run is sorted, this rule identifies the run whose buffered range will be consumed earliest by the merge.

**Initialization with $2k$ input buffers**

1. Create $k$ input-buffer queues, one for each run.
2. Read one block from each run and place it in that run's queue. This uses $k$ buffers.
3. Put $k-1$ unused buffers into the shared free pool.
4. Use the remaining buffer to begin an asynchronous read from the first run predicted to exhaust.
5. Set `activeOutputBuffer = 0`.
6. Initialize the min loser tree with the first record from every run.

**The `kWayMerge` step**

The CPU repeatedly selects the loser-tree winner and copies it to the active output buffer. This step stops when:

- The output buffer becomes full, or
- An end-of-run key is merged into the output buffer (very large value to indicate end of run).

If an input buffer becomes empty during the merge, advance to the next buffer in that run's queue and return the empty buffer to the free pool.

```text
repeat
    kWayMerge into active output buffer
    wait for outstanding input/output to complete

    if an input block completed:
        add its buffer to the queue for its run

    determine which run will exhaust first
    if that run has more input:
        start reading its next block into a free buffer

    start writing the active output buffer
    activeOutputBuffer = 1 - activeOutputBuffer
until an end-of-run sentinel is merged
```

The loser tree selects each next record in $O(\log k)$ time, so merging $N$ records requires $O(N\log k)$ internal processing. Buffering does not change this asymptotic CPU bound; it reduces elapsed time by overlapping CPU work with disk I/O.



> [!CAUTION]
>
> The **“Buffering an External \(k\)-Way Merge”** section does not use a Huffman tree to select individual records.
>
> It uses a **min loser tree**:
>
> - Each external node represents the current record from one run.
> - The winner is the smallest available record.
> - After outputting it, the record is replaced with the next record from the same run.
> - Replay takes \(O(\log k)\).
>
> The Huffman tree and loser tree solve different problems:
>
> | Structure            | Purpose                                                      |
> | -------------------- | ------------------------------------------------------------ |
> | Huffman tree         | Determines the optimal order in which runs of different lengths should be merged |
> | Min loser tree       | Performs one selected \(k\)-way merge by repeatedly finding the smallest record |
> | Input/output buffers | Overlap disk access with the loser-tree merge                |
>
> For example, a Huffman tree might determine:
>
> ```
> First merge:  R1, R2, R3
> Second merge: result, R4, R5
> ```
>
> During each of those merge operations, a loser tree and the buffering strategy perform the actual record-by-record merging.
>
> So the relationship is:
>
> ```
> Huffman tree
>     ↓ decides the merge schedule
> 
> Loser tree + buffers
>     ↓ execute each merge efficiently
> 
> Final sorted run
> ```
>
> The buffering section can operate without Huffman coding—it assumes the \(k\) runs to merge have already been selected.

## 7. Quick Revision

**Complexity and formula summary**

| Concept | Result |
| --- | --- |
| Average replacement-selection run length | Approximately $2k$ |
| Worst input order for replacement selection | Reverse sorted, about $n/k$ runs |
| Replacement-selection CPU time | $O(n\log k)$ |
| Weighted external path length | $\sum_i w_i d_i$ |
| Binary Huffman construction | $O(n\log n)$ using a min heap |
| Dummy nodes for a full $k$-ary tree | $q=(1-r)\bmod(k-1)$ |
| Minimum input buffers for a $k$-way merge | $k+1$ |
| Sufficient dynamically allocated input buffers | $2k$ |
| Output buffers | Exactly 2 |
| Loser-tree $k$-way merge CPU time | $O(N\log k)$ |

**Key takeaways**

1. Replacement selection uses a loser tree to generate runs longer than the available in-memory tree capacity.
2. Frozen records wait for the next run whenever they would violate the order of the current run.
3. For unequal run lengths, total merge cost equals the merge tree's WEPL.
4. Huffman's greedy algorithm constructs a minimum-WEPL binary tree by repeatedly combining the two smallest weights.
5. Prefix-free Huffman codes give frequent messages short codes and minimize weighted transmission and decoding cost.
6. Higher-order Huffman trees may require zero-weight dummy nodes before applying the greedy algorithm.
7. A shared input-buffer pool is more effective than permanently assigning the same number of buffers to every run.
