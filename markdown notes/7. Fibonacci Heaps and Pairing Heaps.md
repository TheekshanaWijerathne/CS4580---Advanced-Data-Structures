# Lecture 07 - Fibonacci Heaps and Pairing Heaps

## 1. Lecture Map

This lecture develops two meldable priority queues:

- **Fibonacci heaps**, which use lazy tree consolidation, parent pointers, and cascading cuts to obtain very strong amortized bounds.
- **Pairing heaps**, which use a much simpler tree representation and a carefully ordered sequence of pairwise melds.

The main theme is the difference between **actual cost** and **amortized cost**. A single operation may take linear time, while the average charge across every possible operation sequence remains logarithmic or constant.

> **Lecture flow:** motivate fast `decreaseKey` using Dijkstra's algorithm -> examine Fibonacci-heap nodes and cascading cuts -> define pairing heaps and compare-link -> study the bad and good ways to rebuild a heap after removing its root -> compare the complexity bounds.

## 2. Why Fast Decrease-Key Matters

In the single-source shortest-path problem, *Dijkstra's* algorithm maintains a tentative distance $d(v)$ for every unreached vertex $v$.

[Dijsktra Recap](<./sample from a previous module/7.Single Source Shortest Path.md>)

<img src="./assets/image-20260926132533319.png" alt="image-20260926132533319" style="zoom:50%;" />

At each step it:

1. removes the unreached vertex with the smallest tentative (Tentative means something is not final, certain, or fully agreed upon, and it may change later. ) distance;
2. makes that distance final;
3. examines outgoing edges from that vertex;
4. decreases some tentative distances when shorter paths are found.

<img src="./assets/lecture07-dijkstra-graph.png" alt="Weighted graph used to motivate Dijkstra's shortest-path algorithm" style="zoom: 33%;" />

<img src="./assets/image-20260926132621364.png" alt="image-20260926132621364" style="zoom:50%;" />

If the graph has $n$ vertices and $e$ edges, the priority queue performs:

- $O(n)$ `removeMin` operations;
- at most $O(e)$ `decreaseKey` operations.

The resulting bounds are:

| Priority-queue implementation | Total time for Dijkstra's algorithm |
| --- | ---: |
| Unsorted array | $O(n^2)$ |
| Binary min heap | $O((n+e)\log n)$ |
| Fibonacci min heap | $O(n\log n+e)$ |

The Fibonacci-heap improvement comes from:

$$
\operatorname{removeMin}=O(\log n)\text{ amortized}
$$

and:

$$
\operatorname{decreaseKey}=O(1)\text{ amortized}
$$

For dense graphs, where $e$ is much larger than $n$, avoiding the extra $\log n$ factor on every edge relaxation is significant.

## 3. Fibonacci Heap Structure and Basic Operations

A min Fibonacci heap is a collection of heap-ordered min trees. Its roots form a *circular doubly linked list*, and a heap pointer identifies the root with the smallest key. *In Binomial heap roots form a circular linked list (not doubly)*

<img src="./assets/image-20260926143242914.png" alt="image-20260926143242914" style="zoom:50%;" />

<img src="./assets/image-20260926171801758.png" alt="image-20260926171801758" style="zoom: 67%;" />

Each node stores:

- `data`: the key and associated item;
- `degree`: the number of children;
- `child`: a pointer to one child;
- `left` and `right`: sibling pointers in a circular doubly linked list;
- `parent`: a pointer to its parent, or `null` for a root;
- `childCut`: a Boolean mark.

<img src="./assets/image-20260926153343009.png" alt="image-20260926153343009" style="zoom: 50%;" />

The `childCut` field records whether a non-root node has already lost a child *since* it became a child of its current parent:

- `false`: it has not yet lost a child;
- `true`: it has lost one child;
- undefined for a root.

Whenever `removeMin` links one root below another, the node that becomes a child receives `childCut = false`.

> [!TIP]
>
> In a Fibonacci Heap, `childCut` is basically a **warning flag** for a node.
>
> Suppose node **B is a child of A**.
>
> - `childCut = false` → B has **not lost any child yet** since B became A’s child.
> - `childCut = true` → B has **already lost one child**.
> - If B loses **another child**, B itself is cut from A and moved to the root list. This is called a **cascading cut**.
>
> Example:
>
> ```
>       A
>       |
>       B
>      / \
>     C   D
> ```
>
> Initially:
>
> ```
> B.childCut = false
> ```
>
> Now suppose `C` is cut away from B:
>
> ```
>       A
>       |
>       B
>       |
>       D
> ```
>
> B has lost its **first child**, so:
>
> ```
> B.childCut = true
> ```
>
> Later, if `D` is also cut away from B, since B already had `childCut = true`, we also cut **B from A**:
>
> ```
> Roots: A    B    C    D
> ```
>
> So you can remember it as:
>
> > **`childCut = true` means: “I already lost one child. If I lose another, cut me from my parent too.”**
>
> For a **root node**, `childCut` does not really matter because a root has no parent to be cut from.
>
> ​    



### Basic Operations

#### **1. Insert and meld**

*Same as binomial heaps*

Insertion creates a singleton tree and splices it into the root list. Meld concatenates two root lists and chooses the smaller of their two minimum pointers.

Neither operation consolidates trees, so both have actual and amortized cost $O(1)$.



#### **2. Remove minimum**

*Same as binomial heaps*

`removeMin` follows the same main idea as the lazy binomial heap:

1. remove the minimum root;
2. promote its children into the root list and set their parent pointers to `null`;
3. consolidate roots of equal degree;
4. rebuild the root list and update the minimum pointer.

A single removal may examine many roots, so its actual worst-case cost is $O(n)$. After amortization, its cost is $O(\log n)$.



*New functions*

#### **3. Remove a specified node**

When a pointer to `theNode` is provided:

<img src="./assets/image-20260926153439937.png" alt="image-20260926153439937" style="zoom:33%;" />

1. detach `theNode` from its sibling list;
2. promote its children into the top-level list;
3. set the promoted children's parent pointers to `null`;
4. perform the required cascading cut above the removed node. 

<img src="./assets/image-20260926160957715.png" alt="image-20260926160957715" style="zoom: 50%;" />

<img src="./assets/image-20260926160926654.png" alt="image-20260926160926654" style="zoom:50%;" />

<img src="./assets/image-20260926160939223.png" alt="image-20260926160939223" style="zoom:50%;" />





If `theNode` is the minimum root, this is simply `removeMin`. A general removal is $O(n)$ actual and $O(\log n)$ amortized.

![image-20260926165321300](./assets/image-20260926165321300.png)

#### 4. Decrease-Key and Cascading Cuts

Suppose the key at node $x$ is decreased.

- If $x$ is a root, no parent-child order can be violated.
- If the new key is still at least its parent's key, no structural change is required.
- If the new key is smaller than its parent's key, *cut* the entire subtree rooted at $x$ and move it to the root list.
- Update the heap's minimum pointer if necessary.

<img src="./assets/image-20260926164324109.png" alt="image-20260926164324109" style="zoom:50%;" />

<img src="./assets/image-20260926164334083.png" alt="image-20260926164334083" style="zoom:50%;" />

```text
decreaseKey(H, x, amount):
    reduce x.key by amount
    y = x.parent

    if y is not null and x.key < y.key:
        cut x from y
        add x to H.rootList
        x.parent = null
        x.childCut = false
        cascadingCut(H, y)

    if x.key < H.min.key:
        H.min = x
```

![image-20260926165329171](./assets/image-20260926165329171.png)

#### Cascading-Cut Rule

**Why one cut is not enough**

Removing a child weakens the structure of its parent. Fibonacci heaps allow a non-root node to lose one child and remain where it is. If it loses another child, the node itself is cut from its parent.

<img src="./assets/image-20260926165717934.png" alt="image-20260926165717934" style="zoom:50%;" />

The cascading rule is:

1. Start at the parent of the node that was cut.
2. If the current node is a root, stop.
3. If `childCut = false`, set it to `true` and stop.
4. If `childCut = true`, cut this node, move it to the root list, clear its mark, and continue with its parent.

![image-20260926170805683](./assets/image-20260926170805683.png)

```text
cascadingCut(H, y):
    z = y.parent

    if z is not null:
        if y.childCut is false:
            y.childCut = true
        else:
            cut y from z
            add y to H.rootList
            y.parent = null
            y.childCut = false
            cascadingCut(H, z)
```

<img src="./assets/lecture07-cascading-cut-start.png" alt="Fibonacci heap before a decrease-key operation triggers cascading cuts" style="zoom:50%;" />

In the example, decreasing the selected key violates heap order. The selected subtree is moved to the root list. Its marked ancestors are also cut until the process reaches an unmarked node, which is marked and left in place.

<img src="./assets/image-20260926170954626.png" alt="image-20260926170954626" style="zoom:50%;" />

<img src="./assets/image-20260926171007960.png" alt="image-20260926171007960" style="zoom:50%;" />

<img src="./assets/image-20260926171017995.png" alt="image-20260926171017995" style="zoom:50%;" />

```
removeMin links node under a parent
        -> ChildCut = false

node loses its first child
        -> ChildCut = true

node loses another child
        -> node is cut and becomes a root
        -> ChildCut is irrelevant

a later removeMin links it under another node
        -> ChildCut = false again
```

The cascade can follow a path of length $O(n)$, so one `decreaseKey` has actual worst-case cost $O(n)$. Its amortized cost is nevertheless $O(1)$.

> ### Why the Amortized Cost Is Constant
>
> Let:
>
> - $t(H)$ be the number of trees in the root list;
> - $m(H)$ be the number of marked non-root nodes.
>
> Choose:
>
> $$
> \Phi(H)=t(H)+2m(H)
> $$
>
> Each cut creates one extra root, increasing $t(H)$. However, every cascading cut after the first removes a marked node and makes it an unmarked root, reducing $m(H)$. The decrease in the $2m(H)$ term pays for continuing up the path. Therefore, the long actual cascade has only $O(1)$ amortized cost.
>
> The marking rule also prevents a non-root node from losing many children while remaining deep in a tree. This gives Fibonacci growth in the minimum number of descendants of a node as its degree increases. Consequently:
>
> $$
> \text{maximum degree}=O(\log n)
> $$
>
> That logarithmic degree bound is what leaves only $O(\log n)$ roots after `removeMin` consolidation.

## 5. Pairing Heap Structure and Compare-Link

A pairing heap is a single heap-ordered multiway tree. It keeps fewer fields and applies simpler structural rules than a Fibonacci heap.

<img src="./assets/lecture07-pairing-heap.png" alt="Example of a max pairing heap" style="zoom: 25%;" />

Each node stores:

- `data`;
- a pointer to its first child;
- left and right sibling pointers.

The sibling list is doubly linked but not circular. The first child's left pointer points to the parent, allowing the first child to be recognized by the condition:

```text
x.left.child == x
```

There is no separate parent, degree, or `childCut` field.

<img src="./assets/image-20260926174936428.png" alt="image-20260926174936428" style="zoom:50%;" />

### Compare-Link Operation

#### 1. Meld

Melding two pairing heaps uses one compare-link operation:

- compare the two roots;
- for a max heap, keep the larger root as the new root;
- make the smaller-rooted tree the leftmost child of the larger root.

For a min heap, keep the smaller root and attach the larger-rooted tree below it.

<img src="./assets/image-20260926175042867.png" alt="image-20260926175042867" style="zoom:50%;" />

Only a constant number of comparisons and pointer changes are needed:

$$
T_{meld}=O(1)\text{ actual}
$$

#### 2. insertion

Insertion creates a singleton tree and melds it with the existing heap, so:

$$
T_{insert}=O(1)\text{ actual}
$$



<img src="./assets/image-20260926175236951.png" alt="image-20260926175236951" style="zoom:50%;" />

<img src="./assets/image-20260926175301660.png" alt="image-20260926175301660" style="zoom:50%;" />

Pairing heaps do not guarantee a logarithmic height or degree. Depending on insertion order:

- the root may have degree $n-1$;
- the tree may have height $n$.

<img src="./assets/lecture07-worst-degree.png" alt="Insertion order that produces degree n minus one in a pairing heap" style="zoom: 33%;" />

<img src="./assets/lecture07-worst-height.png" alt="Insertion order that produces linear height in a pairing heap" style="zoom: 33%;" />

These worst-case shapes explain why an individual removal can take $O(n)$ time.





---

#### 3. Increase Key

*Increasing $x$ cannot violate heap order with its children, but it may make $x$ larger than it**s parent*.* Because the representation has no explicit parent field for every node, the algorithm does not first compare against the parent.

If $x$ is not the root:

1. detach the subtree rooted at $x$ from its sibling list;
2. increase $x$'s key;
3. meld the subtree rooted at $x$ with the remaining heap.

The detach and compare-link use constant pointer operations, so the actual cost is $O(1)$.

For a min pairing heap, the symmetric operation is `decreaseKey`.

## 6. Removing the Root of a Pairing Heap

<img src="./assets/image-20260926181206735.png" alt="image-20260926181206735" style="zoom:67%;" />

Removing the root leaves all its child subtrees as separate pairing heaps. They must be melded into one tree.

If the root has degree $d$, any rebuilding method must inspect its $d$ children, so the actual cost is:

$$
O(d)=O(n)
$$

The order in which the subtrees are melded determines the amortized performance.



### Why One-Pass Melding Is Bad

The tempting method is:

<img src="./assets/image-20260926181448885.png" alt="image-20260926181448885" style="zoom:50%;" />

```c++
currentTree = first subtree

for each remaining subtree from left to right:
    currentTree = compareLink(currentTree, next subtree)
```

<img src="./assets/image-20260926181526655.png" alt="image-20260926181526655" style="zoom:50%;" />



This may repeatedly build an unfavorable structure. The lecture gives a sequence of $n$ inserts followed by $n$ root removals whose removal cost is:

$$
1+2+\cdots+(n-1)=\Theta(n^2)
$$

Thus the one-pass method can have $O(n)$ amortized removal cost.

<img src="./assets/image-20260926182445985.png" alt="image-20260926182445985" style="zoom:33%;" />

> The important point is:
>
> > One removal does **not** cost $\Theta(n^2)$. A sequence of $n$ removals can cost $\Theta(n^2)$ in total.
>
> Suppose the root has $n-1$ children. Removing it requires combining those $n-1$ child subtrees, so the cost is approximately $n-1$ compare-link operations.
>
> With the bad one-pass method, this can produce another unfavorable tree whose new root has $n-2$ children. Therefore, the next removal is also expensive.
>
> ```mermaid
> 
> flowchart LR
>     A["Root has n-1 children<br/>Removal cost: n-1"]
>     B["Root has n-2 children<br/>Removal cost: n-2"]
>     C["Root has n-3 children<br/>Removal cost: n-3"]
>     D["..."]
>     E["Root has 1 child<br/>Removal cost: 1"]
> 
>     A --> B --> C --> D --> E
> 
> ```
>
> For example, with five elements:
>
> | Removal | Number of child trees combined | Cost |
> | ------- | ------------------------------ | ---- |
> | 1       | 4                              | 4    |
> | 2       | 3                              | 3    |
> | 3       | 2                              | 2    |
> | 4       | 1                              | 1    |
> | 5       | 0                              | 0    |
>
> The total removal cost is:
>
> \[ 4+3+2+1=10 \]
>
> In general:
>
> \[ (n-1)+(n-2)+\cdots+2+1 \]
>
> Reversing the order gives the lecture’s expression:
>
> \[ 1+2+\cdots+(n-1) \]
>
> Using the arithmetic-series formula:
>
> \[ 1+2+\cdots+(n-1) = \frac{n(n-1)}{2} = \Theta(n^2) \]
>
> There are $n$ removals, so the amortized cost per removal is:
>
> \[ \frac{\Theta(n^2)}{n} = \Theta(n) \]
>
> Therefore, the bad one-pass method has linear amortized removal cost.
>
> The problem is that it repeatedly produces another root with many children. The two-pass method avoids this by first pairing neighboring subtrees, producing a more balanced rebuilding process.

<img src="./assets/image-20260926182504491.png" alt="image-20260926182504491" style="zoom:50%;" />

### Two-Pass Scheme

The standard two-pass scheme avoids this repeated imbalance.

Pass 1 moves from left to right and melds adjacent pairs:

$$
(T_1,T_2)\to S_1,\quad
(T_3,T_4)\to S_2,\quad\ldots
$$

<img src="./assets/lecture07-two-pass-first.png" alt="First pass of the pairing-heap two-pass melding scheme" style="zoom:50%;" />

If the number of subtrees is odd, the final unpaired tree is included with the last generated result. Pass 2 starts at the rightmost result and melds the remaining results into it from right to left.

<img src="./assets/lecture07-two-pass-second.png" alt="Second pass of the pairing-heap two-pass melding scheme" style="zoom:50%;" />

```text
twoPassMeld(children):
    pair adjacent trees from left to right
    store each compare-link result

    workingTree = rightmost stored result
    meld earlier stored results into workingTree
        from right to left

    return workingTree
```

Pairing adjacent trees prevents one working tree from absorbing every original subtree immediately. The right-to-left second pass then combines trees that already represent groups of earlier trees.

### Multipass Scheme

The multipass scheme uses a FIFO queue:

1. enqueue all child subtrees;
2. remove two trees from the front;
3. compare-link them;
4. enqueue the result;
5. repeat until one tree remains.

<img src="./assets/image-20260926183517195.png" alt="image-20260926183517195" style="zoom:50%;" />

<img src="./assets/image-20260926183529239.png" alt="image-20260926183529239" style="zoom:50%;" />

<img src="./assets/image-20260926183541060.png" alt="image-20260926183541060" style="zoom:50%;" />

<img src="./assets/image-20260926183604009.png" alt="image-20260926183604009" style="zoom:50%;" />

Both the two-pass and multipass schemes give $O(\log n)$ amortized root removal. They have the same asymptotic complexity, but the two-pass scheme generally performs better in experiments.

## 7. Updating and Removing Non-Root Pairing-Heap Nodes

Consider a max pairing heap and a pointer to node $x$.



#### **Increase key**

*Increasing $x$ cannot violate heap order with its children, but it may make $x$ larger than it**s parent*.* Because the representation has no explicit parent field for every node, the algorithm does not first compare against the parent.

If $x$ is not the root:

1. detach the subtree rooted at $x$ from its sibling list;
2. increase $x$'s key;
3. meld the subtree rooted at $x$ with the remaining heap.

The detach and compare-link use constant pointer operations, so the actual cost is $O(1)$.

For a min pairing heap, the symmetric operation is `decreaseKey`.

#### **Remove a specified non-root node**

To remove node $x$:

1. detach $x$ from its sibling list;
2. meld the children of $x$ using the two-pass or multipass scheme;
3. meld the resulting tree with the part of the original heap that remains.

<img src="./assets/image-20260926184027793.png" alt="image-20260926184027793" style="zoom:50%;" />

<img src="./assets/image-20260926184037924.png" alt="image-20260926184037924" style="zoom:50%;" />

<img src="./assets/image-20260926184100329.png" alt="image-20260926184100329" style="zoom:50%;" />

The number of children can be linear, giving $O(n)$ actual cost. With a good subtree-melding scheme, the amortized cost is $O(\log n)$.

## 8. Complexity Summary and Quick Revision

### Fibonacci Heap

| Operation | Actual worst case | Amortized |
| --- | ---: | ---: |
| Insert | $O(1)$ | $O(1)$ |
| Meld | $O(1)$ | $O(1)$ |
| Remove minimum | $O(n)$ | $O(\log n)$ |
| Remove specified node | $O(n)$ | $O(\log n)$ |
| Decrease key in a min heap | $O(n)$ | $O(1)$ |

### Pairing Heap

| Operation | Actual worst case | Amortized upper bound |
| --- | ---: | ---: |
| Insert | $O(1)$ | $O(\log n)$ |
| Meld | $O(1)$ | $O(\log n)$ |
| Remove minimum or maximum | $O(n)$ | $O(\log n)$ |
| Remove specified node | $O(n)$ | $O(\log n)$ |
| Decrease key in a min heap or increase key in a max heap | $O(1)$ | $O(\log n)$ |

<img src="./assets/lecture07-pairing-amortized-comparison.png" alt="Lecture comparison of amortized Fibonacci-heap and pairing-heap bounds" style="zoom:50%;" />

The $O(\log n)$ amortized entries for pairing-heap insert and meld are upper bounds; their direct actual implementations still take $O(1)$.

### Quick Revision

1. Dijkstra's algorithm performs $O(n)$ removals and up to $O(e)$ decrease-key operations.
2. Fibonacci heaps obtain $O(1)$ amortized `decreaseKey` through marks and cascading cuts.
3. The Fibonacci-heap potential $t(H)+2m(H)$ accounts for roots and marked nodes.
4. A Fibonacci heap consolidates equal-degree roots during `removeMin`, not during insert or meld.
5. A pairing heap is one heap-ordered multiway tree with a very small node representation.
6. Pairing-heap meld and insert use a constant-time compare-link operation.
7. Pairing heaps may have linear height and linear root degree.
8. Sequentially melding every child into one working tree is the bad removal strategy.
9. The two-pass scheme pairs left-to-right and accumulates right-to-left.
10. The multipass scheme repeatedly compare-links two trees from a FIFO queue.
11. Both good schemes give $O(\log n)$ amortized removal.
12. Pairing heaps are often faster in practice because their implementation and node structure are simpler, even though Fibonacci heaps have stronger theoretical bounds for insert, meld, and decrease-key.
