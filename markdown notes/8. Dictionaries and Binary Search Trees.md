# Lecture 08 - Dictionaries and Binary Search Trees

This lecture studies dictionaries that support more than exact-key lookup. Search trees can also find the closest qualifying key, visit keys in sorted order, and retrieve an item by its position in that order.

> **Lecture flow:** dictionary operations -> best-fit bin packing -> indexed search trees -> optimal static search trees -> dynamic BST operations -> why balanced search trees are needed.

The two kinds of optimization in this lecture serve different purposes:

- An **optimal static BST** minimizes expected search cost for known access probabilities.
- A **balanced dynamic BST** keeps its height logarithmic as items are inserted and removed.

**Why a hash table is not always sufficient**

<img src="./assets/image-20260927110635571.png" alt="image-20260927110635571" style="zoom:50%;" />

Hash tables offer expected $O(1)$ exact lookup, insertion, and deletion under suitable hashing and load-factor assumptions. 

A basic implementation can take $O(n)$ in the worst case because many keys may collide. Balanced search trees inside collision buckets can improve the bucket-search bound.

However, hash values do not preserve key order. A basic hash table does not directly support efficient:

- **Nearest-match queries:** find the smallest key greater than or equal to a given value.
- **Range queries:** find all keys between two bounds.
- **Indexed queries:** get or remove the item with the third-smallest key.
- **Sorted output:** visit every item in ascending key order.

A BST preserves the ordering rule:

$$
\text{all left-subtree keys}<\text{node key}<\text{all right-subtree keys}
$$

This makes ordered queries natural. Their efficiency depends on the tree's height.

## 2. Best-Fit Bin Packing with a Search Tree

<img src="./assets/image-20260927111553330.png" alt="image-20260927111553330" style="zoom:50%;" />

<img src="./assets/image-20260927111650097.png" alt="image-20260927111650097" style="zoom:50%;" />

Best fit processes items in their given order. For an item of size $s$, choose the bin with the **smallest remaining capacity that is still at least $s$**. If no existing bin can fit the item, open a new bin.

For capacity 10 and item sizes $[4,7,3,6]$:

| Item | Decision | Remaining capacities afterward |
| ---: | --- | --- |
| 4 | Open bin 1 | Bin 1: 6 |
| 7 | Open bin 2 because 7 does not fit in bin 1 | Bin 1: 6, bin 2: 3 |
| 3 | Choose bin 2, which fits exactly | Bin 1: 6, bin 2: 0 |
| 6 | Choose bin 1, which fits exactly | Bin 1: 0, bin 2: 0 |

<img src="./assets/image-20260927112040116.png" alt="image-20260927112040116" style="zoom:50%;" />

<img src="./assets/image-20260927112009354.png" alt="image-20260927112009354" style="zoom:50%;" />

<img src="./assets/image-20260927112058315.png" alt="image-20260927112058315" style="zoom:50%;" />

<img src="./assets/image-20260927112108294.png" alt="image-20260927112108294" style="zoom:50%;" />

This example is optimal because the total size is 20 and two capacity-10 bins are necessary. Best fit is a heuristic; *it is not guaranteed to find an optimal packing on every input.*

### Finding the Nearest Qualifying Key

<img src="./assets/image-20260927114014028.png" alt="image-20260927114014028" style="zoom:50%;" />

Store each bin in a dynamic dictionary as: 

$$
(\text{remaining capacity},\text{bin index})
$$

Duplicate capacities are allowed because different bins may have the same space remaining. An implementation may instead use a unique composite key `(remaining capacity, bin index)`.

Packing an item of size $s$ requires a **lower-bound search**:

$$
\min\{\text{remaining capacity}\mid\text{remaining capacity}\geq s\}
$$

```c++
findBestFit(root, s):
    candidate = null
    x = root

    while x is not null:
        if x.capacity >= s:
            candidate = x
            x = x.left       // try to find a smaller capacity that still fits
        else:
            x = x.right      // x and its left subtree are too small

    return candidate
```

<img src="./assets/image-20260927115429067.png" alt="image-20260927115429067" style="zoom:50%;" />

For size 22, the search visits capacities:

```text
20 -> 40 -> 30 -> 25
```

20 is too small. Capacities 40, 30, and 25 are candidates, with 25 the best. After packing the item, the chosen bin has $25-22=3$ units remaining.



> Remove its old dictionary entry and insert the updated entry. Simply changing 25 to 3 in its current position could violate BST order.

<img src="./assets/image-20260927115444454.png" alt="image-20260927115444454" style="zoom:50%;" />

> [!important]
>
> With a balanced BST, the search, deletion, and insertion each take $O(\log b)$ for $b$ current bins. Since $b\leq n$, processing $n$ items takes:
> $$
> O(n\log n)
> $$

## 3. Indexed Binary Search Trees

<img src="./assets/image-20260927120130416.png" alt="image-20260927120130416" style="zoom:50%;" />

An **indexed BST** augments every node with:

$$
\text{leftSize}(x)=\text{number of nodes in the left subtree of }x
$$

*The field tells us how many items come before that node within its own subtree.*

<img src="./assets/lecture08-indexed-bst.png" alt="Indexed BST with each node's left-subtree size shown in red" style="zoom:50%;" />

> [!important]
>
> In order traversal gives the sorted sequence in BST:

<img src="./assets/image-20260927121831100.png" alt="image-20260927121831100" style="zoom:33%;" />

```text
[2, 6, 7, 8, 10, 15, 18, 20, 25, 30, 35, 40]
```

The lecture uses **zero-based rank**:

$$
\operatorname{rank}(2)=0,\qquad
\operatorname{rank}(15)=5,\qquad
\operatorname{rank}(20)=7
$$

<img src="./assets/image-20260927121910487.png" alt="image-20260927121910487" style="zoom:50%;" />

> `leftSize` is a local rank within a node's subtree. It is not necessarily that node's rank in the whole tree. For example, node 15 has `leftSize = 0` but global rank 5.



### Retrieving an Item by Index

At node $x$, let $L=x.\text{leftSize}$ and let $i$ be the desired index within the current subtree.

<img src="./assets/image-20260927123240491.png" alt="image-20260927123240491" style="zoom:50%;" />

| Condition | Action |
| --- | --- |
| $i=L$ | Return the item at $x$ |
| $i<L$ | Go left, keeping index $i$ |
| $i>L$ | Go right with index $i-L-1$ |

When going right, subtract $L$ for all items in the left subtree and another 1 for the current node.

```python
getByIndex(root, index):
    reject index if it is outside 0 ... size-1
    x = root

    while x is not null:
        if index == x.leftSize:
            return x.element
        if index < x.leftSize:
            x = x.left
        else:
            index = index - x.leftSize - 1
            x = x.right
```

<img src="./assets/image-20260927123256326.png" alt="image-20260927123256326" style="zoom:50%;" />.

<img src="./assets/image-20260927123308834.png" alt="image-20260927123308834" style="zoom:50%;" />

**Example: `getByIndex(10)`**

1. At 20, `leftSize = 7`. Go right with index $10-7-1=2$.
2. At 40, `leftSize = 3`. Go left, keeping index 2.
3. At 30, `leftSize = 1`. Go right with index $2-1-1=0$.
4. At 35, `leftSize = 0`. The index matches, so return 35.

> Only one downward path is followed, so the time is $O(h)$: $O(n)$ for a badly shaped tree and $O(\log n)$ for a balanced one.





### Representing a Linear List

An indexed binary tree can also represent a list: its inorder sequence is the list's order. Here, positions determine the order; the stored values themselves do not have to be sorted.

<img src="./assets/image-20260927150200115.png" alt="image-20260927150200115" style="zoom:50%;" />

| List representation | `get(index)` | Insert at index | Remove at index |
| --- | ---: | ---: | ---: |
| Array | $O(1)$ | $O(n)$ | $O(n)$ |
| Linked chain | $O(n)$ | $O(n)$ | $O(n)$ |
| Indexed AVL tree | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ |

<img src="./assets/image-20260927150223882.png" alt="image-20260927150223882" style="zoom: 50%;" />



The linked-list bounds include locating the requested index. Inserting next to an already known node can be constant time, but finding that node by index is linear.

An indexed balanced tree must maintain its size information during insertion, deletion, and rebalancing. When a node gains or loses an item in its left subtree, its `leftSize` changes; rotations also require local size updates.





**Experiment in the lecture**

The slides report 40,000 operations of each type using Java on a 350 MHz PC:

<img src="./assets/lecture08-indexed-performance.png" alt="Lecture benchmark comparing arrays, linked chains, and indexed AVL trees for 40000 operations" style="zoom:50%;" />

Arrays are fastest for direct indexed access in this experiment, while indexed AVL trees handle positional insertions and removals much more efficiently. These are historical measurements for the stated setup, not general timings for current hardware.

## 4. Static Dictionaries and Expected Search Cost

<img src="./assets/image-20260927152617590.png" alt="image-20260927152617590" style="zoom:50%;" />

<img src="./assets/image-20260927152630009.png" alt="image-20260927152630009" style="zoom:50%;" />

### Perfect Hashing or a Search Tree?

**Search Tree is better for Dictionaries,** 

> ### Hashing is also possible for Static dictionaries
>
> When the key set is fixed, it can be used to construct a hash function specifically for those keys.
>
> - **Perfect hashing:** no two stored keys collide.
> - **Minimal perfect hashing:** the $n$ stored keys map to exactly $n$ positions.
>
> The lecture cites CHD (Compress, Hash and Displace) as a construction with $O(n)$ construction time and $O(1)$ function evaluation under its hashing assumptions. Minimality concerns the output positions; it does not mean the hash-function description and records require no additional storage. [CHD project documentation](https://cmph.sourceforge.net/chd.html)
>
> 
>
> An absent key may still map to an occupied position, so a dictionary must verify the stored key to recognize an unsuccessful lookup. *Perfect hashing also does not solve ordered queries such as nearest match or range search.*

For a static BST, suppose we know how frequently each key is requested. A frequently requested key benefits from being closer to the root.

<img src="./assets/image-20260927161144511.png" alt="image-20260927161144511" style="zoom: 50%;" />



The taller tree is cheaper on average because the most likely request finishes immediately. *An optimal BST minimizes this weighted search cost, rather than height alone.*



### Successful and Unsuccessful Searches

<img src="./assets/image-20260927153158293.png" alt="image-20260927153158293" style="zoom: 50%;" />

In this extended-tree representation, the $n$ key-containing nodes are called internal nodes, even if they have no real children. Replacing every missing child pointer with a failure node gives $n+1$ external nodes:

$$
f_0,f_1,\ldots,f_n
$$

<img src="./assets/image-20260927161216903.png" alt="image-20260927161216903" style="zoom:50%;" />

Each failure node corresponds to one gap:

- $f_0$: search key is less than $a_1$.
- $f_i$, for $1\leq i<n$: $a_i<\text{search key}<a_{i+1}$.
- $f_n$: search key is greater than $a_n$.
- <img src="./assets/image-20260927161240917.png" alt="image-20260927161240917" style="zoom: 67%;" />



Let $p_i$ be the probability of searching successfully for $a_i$, and $q_i$ the probability of an unsuccessful search ending at $f_i$. Then:

$$
\sum_{i=1}^{n}p_i+\sum_{i=0}^{n}q_i=1
$$

### The Cost Formula

<img src="./assets/image-20260927161313003.png" alt="image-20260927161313003" style="zoom:50%;" />

The lecture numbers levels starting at **1 for the root**. Search cost counts comparisons with stored keys:

- A successful search at level $\ell$ makes $\ell$ key comparisons.
- A failed search reaching an external node at level $\ell$ makes $\ell-1$ key comparisons, because the external node contains no key to compare.

Therefore:

$$
C(T)=
\sum_{i=1}^{n}p_i\operatorname{level}(a_i)
+\sum_{i=0}^{n}q_i\bigl(\operatorname{level}(f_i)-1\bigr)
$$

For the balanced three-key tree above, every failure node is at level 3. Each failed search compares two real keys, so its contribution is $2q_i$.



An **optimal binary search tree** minimizes $C(T)$ over all BSTs for the given keys and probabilities. *Unlike a Huffman tree, it must preserve the key order*, and successful searches finish at key-containing nodes rather than message leaves.

<img src="./assets/image-20260927161428194.png" alt="image-20260927161428194" style="zoom:50%;" />

Brute force would enumerate all BST shapes and evaluate each cost. The number of shapes is the Catalan number:
$$
C_n=\frac{1}{n+1}\binom{2n}{n}
=\Theta\left(\frac{4^n}{n^{3/2}}\right)
$$

This grows exponentially, motivating dynamic programming.

## 5. Building an Optimal BST with Dynamic Programming

### Subproblems and Base Cases

The lecture uses the following interval convention:

$$
T_{ij}=\text{least-cost tree containing }a_{i+1},\ldots,a_j
$$

There are $j-i$ keys in this tree. The first index is the gap immediately before the first included key, so $T_{ij}$ begins with $a_{i+1}$, not $a_i$.

For example, $T_{2,7}$ contains keys $a_3,\ldots,a_7$ and failure nodes $f_2,\ldots,f_7$:

<img src="./assets/image-20260927184621899.png" alt="image-20260927184621899" style="zoom: 67%;" />

<img src="./assets/image-20260927193353767.png" alt="image-20260927193353767" style="zoom: 67%;" />

<img src="./assets/image-20260927193839838.png" alt="image-20260927193839838" style="zoom: 50%;" />

> 
>
> | Symbol | Meaning |
> | --- | --- |
> | $T_{ij}$ | Optimal tree for keys $a_{i+1},\ldots,a_j$ |
> | $c_{ij}$ | Cost of that tree, measured with its own root at level 1 |
> | $r_{ij}$ | Index of the key chosen as its root |
> | $w_{ij}$ | Total probability of all successful and failed searches in this interval |
>
> The weight is:
>
> $$
> w_{ij}=\sum_{u=i+1}^{j}p_u+\sum_{u=i}^{j}q_u
> $$
>
> These are the original probabilities; do not renormalize them separately for each subtree.
>
> When $i=j$, the interval contains no keys and only the failure node $f_i$:
>
> $$
> c_{ii}=0,\qquad r_{ii}=0,\qquad w_{ii}=q_i
> $$
>
> The cost is zero because there are no stored keys to compare. The weight is still $q_i$, because searches can reach this empty subtree. Here `r = 0` is a sentinel meaning no key-containing root.
>
> ### Deriving the Recurrence
>
> Suppose we choose $a_k$ as the root of $T_{ij}$, where $i<k\leq j$.
>
> The BST ordering rule determines the two subproblems:
>
> $$
> \text{left subtree}=T_{i,k-1},\qquad
> \text{right subtree}=T_{k,j}
> $$
>
> The right subtree starts at $a_{k+1}$, which is why its interval is $T_{k,j}$.
>
> When we attach a subtree below the new root, every search within it performs one extra comparison. Thus:
>
> | Part | Contribution to the complete tree's cost |
> | --- | --- |
> | Left subtree | $c_{i,k-1}+w_{i,k-1}$ |
> | Right subtree | $c_{k,j}+w_{k,j}$ |
> | Root key itself | $p_k$ |
>
> The two subtree weights and the root probability together cover all searches in the interval:
>
> $$
> w_{i,k-1}+w_{k,j}+p_k=w_{ij}
> $$
>
> Therefore, choosing root $a_k$ gives cost:
>
> $$
> c_{i,k-1}+c_{k,j}+w_{ij}
> $$
>
> <img src="./assets/lecture08-obst-root-split.png" alt="Splitting an optimal BST at root ak and adding each subtree's weight for the extra comparison" style="zoom:50%;" />
>
> We do not know which root is best, so try every allowed $k$:
>
> $$
> \boxed{
> c_{ij}=w_{ij}+\min_{i<k\leq j}
> \left(c_{i,k-1}+c_{k,j}\right)
> }
> $$
>
> Store the minimizing $k$ in $r_{ij}$.
>
> > **Why add $w_{ij}$?** Every search represented by this interval compares against its new root once. Multiplying that extra comparison by the probability of each possible search, then adding, gives exactly $w_{ij}$.
>
> This recurrence uses **optimal substructure**: once a root is fixed, both subtrees must be optimal for their intervals. Replacing an inferior subtree with a cheaper one would improve the entire tree without changing BST order.
>
> ### Filling the Tables and Reconstructing the Tree
>
> Compute intervals in increasing order of their number of keys:
>
> ```text
> 0-key intervals: c[i,i]
> 1-key intervals: c[i,i+1]
> 2-key intervals: c[i,i+2]
> ...
> n-key interval:  c[0,n]
> ```
>
> <img src="./assets/lecture08-obst-table-order.png" alt="Upper-triangular cost table filled by diagonals from zero-key intervals to the whole tree" style="zoom:50%;" />
>
> The weights can also be built incrementally:
>
> $$
> w_{ij}=w_{i,j-1}+p_j+q_j
> $$
>
> ```text
> for i = 0 to n:
>     c[i,i] = 0
>     r[i,i] = 0
>     w[i,i] = q[i]
> 
> for length = 1 to n:
>     for i = 0 to n-length:
>         j = i + length
>         w[i,j] = w[i,j-1] + p[j] + q[j]
>         c[i,j] = infinity
> 
>         for k = i+1 to j:
>             candidate = c[i,k-1] + c[k,j] + w[i,j]
>             if candidate < c[i,j]:
>                 c[i,j] = candidate
>                 r[i,j] = k
> ```
>
> There are $O(n^2)$ intervals and up to $O(n)$ root candidates per interval:
>
> $$
> \text{time}=O(n^3),\qquad \text{space}=O(n^2)
> $$
>
> Once the root table is complete, build the tree recursively:
>
> ```text
> build(i, j):
>     if i == j:
>         return null       // conceptually the failure node f[i]
> 
>     k = r[i,j]
>     x = node containing the item with key a[k]
>     x.left = build(i, k-1)
>     x.right = build(k, j)
>     return x
> ```
>
> Call `build(0, n)`. Each key becomes one node, so reconstruction takes $O(n)$ time. It does not repeat the search over root choices.
>
> 
>
> **The $O(n^2)$ improvement**
>
> Knuth's root-monotonicity property, with consistent tie-breaking between equal-cost roots, gives:
>
> $$
> r_{i,j-1}\leq r_{ij}\leq r_{i+1,j}
> $$
>
> After initializing one-key intervals, longer intervals need only test roots between these two bounds, inclusive. This reduces the total number of candidate tests to $O(n^2)$; it does not mean every individual interval tests only a constant number of roots. [Optimal-BST notes, University of Texas at Arlington](https://ranger.uta.edu/~weems/NOTES5311/obst.pdf)
>
> > The optimized formula on slide 48 prints a strict lower inequality. The lower endpoint must be included: $r_{i,j-1}\leq k\leq r_{i+1,j}$. Otherwise, a valid optimal root can be skipped.
>

### Small Worked Example

Consider two keys $a<b$ with:

$$
p_1=0.30,\quad p_2=0.20,\quad
q_0=0.10,\quad q_1=0.15,\quad q_2=0.25
$$

The probabilities sum to 1. Here $q_0$ represents searches below $a$, $q_1$ searches between $a$ and $b$, and $q_2$ searches above $b$.

**Empty intervals:**

$$
c_{00}=c_{11}=c_{22}=0
$$

**One-key intervals:** only one choice of root is possible.

$$
c_{01}=w_{01}=q_0+p_1+q_1=0.55
$$

$$
c_{12}=w_{12}=q_1+p_2+q_2=0.60
$$

**Two-key interval:** $w_{02}=1$.

| Root choice | Left cost | Right cost | Total |
| --- | ---: | ---: | ---: |
| $a$ ($k=1$) | $c_{00}=0$ | $c_{12}=0.60$ | $0+0.60+1=1.60$ |
| $b$ ($k=2$) | $c_{01}=0.55$ | $c_{22}=0$ | $0.55+0+1=1.55$ |

Therefore:

$$
c_{02}=1.55,\qquad r_{02}=2
$$

The optimal tree has $b$ at the root and $a$ as its left child. Its expected comparisons can be checked directly:

$$
0.30(2)+0.20(1)+0.10(2)+0.15(2)+0.25(1)=1.55
$$

Even though $a$ is the more frequently requested stored key, the failed-search probabilities make $b$ the better root.

## 6. Dynamic BST Operations

<img src="./assets/image-20260927195640892.png" alt="image-20260927195640892" style="zoom:50%;" />

A dynamic dictionary supports search, insertion, and deletion as its collection changes. Search trees can additionally support ascending traversal and, when augmented with size information, indexed access and deletion.

<img src="./assets/image-20260927202707408.png" alt="image-20260927202707408" style="zoom:50%;" />

<img src="./assets/image-20260927202716527.png" alt="image-20260927202716527" style="zoom:50%;" />



### Search and Insertion

For search, compare the requested key with the current node and follow the appropriate child. Insertion follows the same path until reaching a missing child position, where the new node is attached.

<img src="./assets/image-20260927202801305.png" alt="image-20260927202801305" style="zoom:50%;" />

For example, inserting key 35 into the lecture's tree before 35 is present follows:

```text
20 -> 40 -> 30 -> missing right child
```

Both operations take $O(h)$ time in a BST of height $h$.

### Deletion: Three Cases

<img src="./assets/image-20260927202812681.png" alt="image-20260927202812681" style="zoom: 33%;" />

**1. The node is a leaf.** Remove it and set the corresponding parent pointer to `null`. In the lecture tree, key 7 is a leaf.

<img src="./assets/image-20260927202848187.png" alt="image-20260927202848187" style="zoom:50%;" />

**2. The node has one child.** Link its parent directly to its child. If deleting the root, update the tree's root pointer instead. Examples include replacing 40 with its child 30, or replacing 15 with its child 18.

<img src="./assets/image-20260927202857778.png" alt="image-20260927202857778" style="zoom: 33%;" />

<img src="./assets/image-20260927202906894.png" alt="image-20260927202906894" style="zoom: 33%;" />

**3. The node has two children.** Replace its key and associated element with either:

- the **inorder predecessor**, which is the largest key in its left subtree; or
- the **inorder successor**, which is the smallest key in its right subtree.

Then delete the predecessor/successor from its old location. That node has at most one child, so the remaining deletion is one of the simpler cases.

<img src="./assets/image-20260927202942956.png" alt="image-20260927202942956" style="zoom:33%;" />

<img src="./assets/image-20260927202951828.png" alt="image-20260927202951828" style="zoom:33%;" />

<img src="./assets/image-20260927203004509.png" alt="image-20260927203004509" style="zoom:33%;" />

## 7. Priority-Queue Operations and the Need for Balance

**Minimum and maximum**

<img src="./assets/image-20260927203336410.png" alt="image-20260927203336410" style="zoom:50%;" />

In a BST, the minimum is reached by following left children, while the maximum is reached by following right children. Finding or removing either extreme takes $O(h)$ without additional cached information.

Unlike a min heap, a BST does not necessarily store its minimum at the root. Its stronger ordering supports searches throughout the key range.



**Initialization from unsorted input**

<img src="./assets/image-20260927203346084.png" alt="image-20260927203346084" style="zoom:33%;" />

Constructing a BST containing arbitrary comparison-based keys requires $\Omega(n\log n)$ comparisons in the worst case. Otherwise, constructing the tree and then performing an $O(n)$ inorder traversal would sort arbitrary inputs faster than the comparison-sorting lower bound.

A matching construction sorts the keys and recursively chooses middle keys as roots, taking $O(n\log n)$ overall. If the input is already sorted, the balanced tree can be built in $O(n)$.





**Melding two BSTs**

<img src="./assets/image-20260927203648213.png" alt="image-20260927203648213" style="zoom:50%;" />

<img src="./assets/image-20260927203657562.png" alt="image-20260927203657562" style="zoom:50%;" />

The keys from two BSTs may be arbitrarily interleaved. A general meld can:

1. traverse both trees in order;
2. merge the two sorted sequences;
3. build a balanced BST from the result.

For trees with $m$ and $n$ items, this takes $O(m+n)$ time. Merging two sorted lists of size $n$ each may need $2n-1$ comparisons, and general comparison-based BST melding has a linear worst-case lower bound. Thus it cannot promise the constant or logarithmic meld cost seen in the specialized priority queues from earlier lectures.

This concerns unrestricted meld. Joining trees whose key ranges are already known to be disjoint and ordered is a different operation.

### Why Not Force a Complete Tree?

A perfect binary tree has all levels filled and can only have:

$$
n=2^k-1
$$

nodes for some number of levels $k$. The lecture calls these trees "full"; "perfect" makes the all-levels-filled condition explicit.

A complete binary tree can exist for every $n$, but maintaining both its exact complete shape and BST order can require many nodes to move when one key is inserted or deleted.

<img src="./assets/lecture08-complete-tree-insertion.png" alt="Inserting key 1 changes several node positions when both complete-tree shape and BST order are enforced" style="zoom:50%;" />

Balanced search trees use more flexible structural rules that preserve $O(\log n)$ height while allowing $O(\log n)$ updates. The lecture introduces these families:

| Balancing approach | Idea or examples |
| --- | --- |
| Height balance | Restrict subtree-height differences; AVL trees |
| Weight balance | Restrict imbalance in subtree sizes |
| Degree balance | Control multiway node sizes; 2-3 trees, 2-3-4 trees, B-trees; red-black trees encode related balancing constraints in binary form |

## 8. Quick Revision

| Need | Structure or technique from this lecture |
| --- | --- |
| Expected constant-time exact-key operations | Hash table |
| Collision-free lookup for a fixed key set | Perfect hashing |
| Smallest key at least a threshold | BST lower-bound search |
| Best-fit bin packing in $O(n\log n)$ | Balanced dictionary keyed by available capacity |
| Access an item by sorted position | Indexed BST with subtree counts |
| Logarithmic positional list updates | Indexed balanced tree |
| Minimize expected static search cost | Optimal BST using access probabilities |
| Guarantee logarithmic dynamic dictionary operations | Balanced search tree |

**Formulas to remember**

For indexed lookup, go right with:

$$
\text{new index}=\text{index}-\text{leftSize}-1
$$

For an optimal BST with the root at level 1:

$$
C(T)=\sum_{i=1}^{n}p_i\operatorname{level}(a_i)
+\sum_{i=0}^{n}q_i\bigl(\operatorname{level}(f_i)-1\bigr)
$$

$$
c_{ii}=0,\qquad w_{ii}=q_i
$$

$$
c_{ij}=w_{ij}+\min_{i<k\leq j}\left(c_{i,k-1}+c_{k,j}\right)
$$

**Common mistakes**

- Treating `leftSize` as the node's global rank.
- Forgetting to subtract 1 for the current node when going right.
- Including $a_i$ in $T_{ij}$; the first included key is $a_{i+1}$.
- Setting $w_{ii}=0$ even though the empty interval still has failure probability $q_i$.
- Counting an extra key comparison at an external failure node.
- Assuming the most balanced tree always has the lowest expected search cost.
- Changing a dictionary key in place without restoring BST order.
- Assuming every ordinary BST has logarithmic height.
